Method notes: event-loop numbers come from `monitorEventLoopDelay` (10 ms resolution) in the main process; IPC bytes are JSON-length of args plus results and are switched off while the app-list refresh is timed so the probe does not add to the event-loop delay; CPU is the cumulative user+kernel time of the whole process tree (Electron processes plus llama-server and any Python sidecar) divided by wall time. Cold-start budget uses a 5% noise allowance, the other relative budgets 10% (plus a small absolute floor on near-zero metrics).

## How the baseline and the noisy metrics were taken

- Baseline: tag v1.0.98 (dc53493) built in a scratch worktree with the CURRENT `scripts/perf` harness. v1.0.98 already contains the identical `electron/perf-probe.ts` and probe wiring (`apply-probes.mjs` was a no-op, `scripts/perf` is unchanged between the tag and HEAD).
- Full runs (10 cycles, 60 s idle, 120 s hidden idle, models, AI phase): v1.0.98 twice, main once.
- Three metrics read a single short window and swing between identical builds, so they are medians over repeated narrow runs, applied the same way to both sides (`--hidden-only --hidden-idle-s 120` and `--ai-only`, alternating builds):
  - Hidden idle CPU: v1.0.98 8 samples 0.10-0.58 % (median 0.33), main 7 samples 0.16-0.61 % (median 0.41). The ranges overlap; in every sample the cost is one to five ~0.1 s renderer wake-ups (a burst near 70 s after hiding appears in both builds), well under the 1 % absolute budget.
  - llama-server idle CPU per role: v1.0.98 5 samples (embed 1.05-2.67, rerank 1.48-2.2), main 4 samples (embed 1.48-1.86, rerank 1.79-2.3); medians stored.
  - Idle CPU 60 s: v1.0.98 15.08 and 14.91 % (stored 15.0); main 16.55 % (one sample, +10.3 %, inside the +13 % limit).
- Everything else is from the single full run of each side. Against the first v1.0.98 run alone the verdict is also PASS; against the second v1.0.98 run alone, hidden idle (0.10 %) and llama idle (1.48 %) would fail by their relative limit, which the repeated samples show is baseline noise, not a regression.
- "Router overhead -9.3 %" in the table is main's through-the-app burst reading faster than direct HTTP in that run (both within run-to-run spread of the 32+32 item burst); the budget is 15 % overhead.
