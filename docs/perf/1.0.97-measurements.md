## Measurement changes made in this round (applied to both builds)

- **Baseline rebuilt with ML data.** `dataset/` is git-ignored, so the clean v1.0.96 checkout could not load the model. The model files were copied in (`game_profiles.json`, `feature_spec.json`, `tag_mapping.json`, `onnx_ensemble/`) and the baseline re-measured: cycles 1-3 from one run (the build leaks ~130k DOM nodes per cycle and its cycle time grows), idle / hidden-idle / app-list from a second run. Every number that depended on the model moved (RSS, idle CPU, boot event loop, cold start).
- **Windows occlusion detection off** (`--disable-features=CalculateNativeWinOcclusion --disable-backgrounding-occluded-windows`): when another window covered the app, Playwright's rAF-based stability check never returned and "Enter Ark" could not be clicked (seen in several runs).
- **Hidden idle:** the window is hidden only after the Browse visit's offline Top Sellers retry chain has run out (`--hidden-settle-s`, default 45 s: egdata / Epic retries with 4 s and 6 s waits start on every Browse visit); the probe's own 10 ms event-loop sampler (~2% of a core in the main process, independent of the app) is switched off while hidden idle is measured. A blank Electron window under the same Playwright launch idles at 0.07% hidden, and v1.0.96 measures 0.07% the same way.
- **GPU memory after Ark:** waits for the settle described above.
- **Event-loop max budget:** compared as the median of the per-cycle maxima. A maximum over all cycles grows with the cycle count (10 vs 3 here) and is set by one stall; the single worst spike stays in the table as an informational row (v1.0.96 260 ms in 3 cycles; this build 352 ms, seen at cycles 3, 7 and 10, about every 5 minutes, which matches the offline catalog retry cooldown reading the 155k-entry app list).
- `--heap-snapshots` was not used in the final run (no leak rule failed); the earlier snapshot analysis showed only harness-owned growth.

## Round 2: hidden idle CPU (1.77% vs 0.07%)

Result: **not an app defect; a measuring-environment artifact. Fixed in the harness, with the evidence below.** The budget is now measured the way a user's tray-hidden window runs (no automation client attached): 0.14% for this build and 0.14% for v1.0.96 (limit < 1% and < 0.45%).

What was found (all with `scripts/perf/hidden-probe.mjs`, same seeded profile, same machine):

1. **The cost starts at one moment, about 22 s after the window is hidden.** Per-10 s CPU series (Playwright attached): GPU 0.02%, renderer 0.15% until +20 s, then GPU 1.6% and renderer 1.6% from +30 s onwards, flat. The moment is the auto On Hold sweep (`useAutoOnHold`, first run 75 s after launch): its toast ("234 games moved to On Hold ...") is added to the DOM while the window is hidden (MutationObserver: "22s 234 games moved ..."). Hiding after the sweep and its toast are over (settle 110 s) gives GPU 0.01%, renderer 0.03% for the same build. So it is not a loop in the app: v1.0.97 idles at ~0 hidden unless something animates while hidden.
2. **What the loop is.** Right after the toast, `document.getAnimations()` holds one framer-motion Web Animation with `pending = true` and `document.timeline.currentTime` does not advance (75276.5 on two reads 2 s apart). A 8 s content trace in that state shows 482 `ExternalBeginFrameSource::OnBeginFrame` / `Scheduler::BeginImplFrame` / `AnimationHost::TickAnimations` in both the renderer and the GPU process (60 per second), 482 `SetNeedsRedrawOnImplThread`, and no main-thread work in between: the compositor keeps ticking for an animation that is waiting for a frame commit a hidden window never produces. Cancelling the animation does not stop it (CPU unchanged afterwards); showing the window does.
3. **It is the attached automation client, not the app.** Page visibility reports `visible` for a hidden or minimized window in this setup (BrowserWindow.hide() and minimize() both leave `document.visibilityState === 'visible'`), so Chromium keeps its BeginFrame source running for Playwright's CDP session. **Control on v1.0.96, attached the same way: one 300 ms `document.body.animate()` started while the window is hidden gives GPU 1.79% + renderer 1.73% (plus the same flat series) for the rest of the window**, i.e. the identical stuck state with no toast involved. v1.0.96 only measured 0.07% because nothing animated while its window was hidden (in the full scenario the window is hidden minutes after launch, and its probe run showed no toast while hidden).
4. **Detached, there is no such loop.** Same app, launched directly with a remote-debugging port used only to click "Enter Ark" and open Browse, hidden through the app's own title-bar minimize (hide to tray), socket closed, CPU read from OS counters. Even with the sweep toast landing while hidden (a diagnostic run that hid the window 45 s after Browse, ~75 s uptime): a renderer burst of about 1.1 s CPU in the one sampling interval around the toast (the sweep and the toast render), then 0.0-0.4% per interval, GPU process 0 s for the whole window. Steady state after the burst: GPU 0 s, renderer 0.1 s, browser 0.06 s over 120 s.

What changed in the harness (applies to both builds):

- `scripts/perf/lib/detached.mjs` (new): the hidden-idle budget is measured detached as described in 4. The window is hidden at Browse after at least 150 s of app uptime (the full scenario hides it minutes after launch, so the 75 s sweep and its 15 s toast are done; a fresh launch must wait for the same thing, otherwise the window measures the sweep). 10 s per-process series and the list of toasts added while hidden are stored in the result.
- `measure.mjs`: `hiddenIdle` is the detached number. The Playwright-attached number is kept as `hiddenIdleAttached` (informational, `--attached-hidden`) and shown in the "Hidden idle detail" table. `--hidden-only [--merge-into result.json]` re-runs just this phase. Baseline and current JSON were both re-measured with it (120 s each); the baseline's old attached value (0.07%) is kept as `hiddenIdleAttached`.
- `launch.mjs`: `PERF_KEEP_OCCLUSION=1` omits the two occlusion flags (diagnostics only; made no difference to the result).
- `hidden-probe.mjs` (new): the diagnostic used above (series, trace, animation dump, `--inject-anim`, `--cancel-anims`, `--toasts`).

Why this is not a loosened budget: the budget (< 1% and not more than 10% + 0.3 points over v1.0.96), the scenario, the 120 s window and the process set (whole tree: browser, GPU, utility, renderer, any sidecar) are unchanged; the only change is that no automation client is attached while the window is hidden, which is how the window is hidden to the tray in real use. Both builds pass or fail the same way under either method for the same reason (the control in point 3), so the comparison is unchanged in fairness.

Tests: `src/test/perf-analyze.test.mjs` "hidden idle budget reads the detached measurement, never the attached one". No app code changed in this round, so there is no app regression test; the app side of the sweep (one batched notification) is already covered by `useAutoOnHold.test.ts`.

## Not fixed

- Nothing in the budgets or leak rules fails. Informational: visible idle CPU is 14.84% vs 13.2% (+12.4%), inside the limit of 15.02% (10% plus the 0.5 point floor). The auto On Hold sweep still costs the renderer about 1 s of CPU once, 75 s after launch, whether or not the window is hidden (the toast and the 234 library updates re-render); it is a one-shot (then hourly, a no-op once the games are moved) and is not part of idle.

## Reproducing

```
node scripts/perf/measure.mjs --label main --out main.json --cycles 10 --hidden-idle-s 120
node scripts/perf/measure.mjs --report --current docs/perf/data/1.0.97-main.json --baseline docs/perf/data/v1.0.96-baseline.json --md docs/perf/1.0.97-measurements.md
```

`ARK_PERF_CPUPROF=1` additionally profiles the main process from its first line (`__arkPerf.stopCpuProfile(file)` writes the `.cpuprofile`), which is how the ONNX and renderer `put` costs above were found.
