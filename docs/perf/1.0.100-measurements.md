# 1.0.100 measurements

1.0.100 changes only the Oracle (shelf layout, match percentages, engine 16): `electron/` is byte-identical to 1.0.99
(`git diff 8be83e5..HEAD -- electron` is empty), so main-process budgets cannot move because of it. The measurement
focus is the renderer: leaks across the full scenario and a paired A/B against the 1.0.99 build.

## What ran

- Full 10-cycle scenario, built-in AI models on, 2000-game test profile (copied userData, no real keys):
  heap 52 -> 63.8 MB (flat from cycle 3), DOM nodes 3860 every cycle (v1.0.98: 3861), JS listeners 3352 every cycle,
  IPC listeners 13-14, 8 processes, 2 llama-servers throughout. No leak rule fired on the leak metrics.
- Quick 3-cycle run (no models): heap 38-39 MB, nodes 3846 flat.
- Paired A/B, 5 cycles each, same machine and profile, 1.0.99 build vs 1.0.100 build: heap 39.07 vs 39.12 MB, DOM
  3846 vs 3846, event-loop max and longest task in the same range; main RSS and total working set equal once both
  trees carry the same `dataset/ml` and runtime folders.

## Runs that were discarded, and why

- First full run: the machine stalled for hours mid-scenario; the `back-to-browse` step timed out and the DOM readings
  that followed (+25k nodes per cycle) came from a page stuck mid-step, not from the app. A clean rerun is flat.
- A run overlapped with a second harness run on the same machine (idle CPU 29 %), so it was thrown away.
- Early A/B pairs compared against a 1.0.99 worktree that lacked `build/llama-runtime`, `build/litellm-runtime` and
  `dataset/ml`; its main process therefore skipped the ML model load (~+200 MB RSS, shorter boot). With those linked the
  RSS gap closed.

## Known noise

The host was running corporate security scanners at 30-60 % total CPU during these runs, which inflates cold-start,
boot event-loop max, download and app-list event-loop numbers for both builds (same 1.0.99 build measured 311-407 ms
boot loop max on different runs). No budget was loosened. The per-release baseline for these load-sensitive metrics
should be re-sampled on a quiet machine (see 1.0.98 note on median-of-runs baselines).
